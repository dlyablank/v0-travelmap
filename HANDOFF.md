# Передача Weekend Explorer в локальный чат

Актуально на 20 октября 2026 года. Это передача существующего проекта, а не предложение переписать его с нуля.

## Цель и договорённости с пользователем

Пользователь хочет продолжать разработку в локальном чате на своём компьютере: направлять продукт, а агент должен самостоятельно выполнять обычный цикл разработки, проверок и обновления сайта. Сейчас задача — оценить направление интерфейса и пользовательский сценарий, затем развивать MVP по обратной связи. Конкретных новых изменений дизайна после первого просмотра ещё не согласовывали.

Исходное полное задание сохранено в [docs/PRODUCT_BRIEF.md](docs/PRODUCT_BRIEF.md). Главный принцип — **video-first, map-first**: исследование настоящих мест через карту и вертикальные видео, превращение выбранных мест в поездку. Не делать маркетинговый лендинг или обычный каталог с маленькой картой сбоку. Язык — русский, светлая тема, коралловый акцент, адаптивный desktop/mobile.

Пользователь не хочет лишних подтверждений для обычных действий. При этом доступ к компьютеру, браузеру и учётным записям определяется фактическими инструментами и разрешениями новой локальной сессии. Этот документ сам по себе таких прав не предоставляет. Вход в сервисы пользователь готов подтвердить самостоятельно; пароли и токены не запрашивать в чате.

## Локальный запуск для оценки интерфейса

Нужны Git, Node.js **24.x** и npm. Команды подходят для обычного терминала, в том числе PowerShell:

```sh
git clone https://github.com/dlyablank/v0-travelmap.git
cd v0-travelmap
npm ci
npm run db:generate
npm run dev
```

Если папка уже клонирована — сначала проверить `git status`, не перезаписывать местные изменения и не клонировать поверх неё.

Для первого демо **не создавать `.env.local` и не задавать `DATABASE_URL`**. Тогда приложение использует встроенные 24 точки, localStorage для поездки/закладок и не требует Docker, PostgreSQL, S3 или API-ключей. Открыть в браузере пользователя `localhost:3000`.

Обычная команда установки — `npm ci`; `scripts/setup.sh` содержит облачный путь к npm cache `/workspace/.npm-cache`, поэтому не запускать его на ПК без адаптации. В `README.md` и `START-HERE.md` есть дополнительные инструкции; для локального демо приоритет у приведённых выше команд.

Не запускать `next dev` и `next build` одновременно в одном checkout: оба используют `.next`. Останавливать только процессы, запущенные для этого проекта. Для Windows не использовать команды Bash без проверки доступности Bash/WSL.

## Локальный полный стек (когда действительно понадобится)

Для визуальной оценки сначала достаточно демо. Для сохранения импортированных мест в PostgreSQL и загрузки собственных MP4:

1. Создать `.env.local` из `.env.example`, только если собственного файла ещё нет. В PowerShell: `Copy-Item .env.example .env.local`; в Bash: `cp .env.example .env.local`. Не перезаписывать существующий файл.
2. Запустить Docker и `docker compose up -d postgres`. Дождаться readiness PostgreSQL (например, `docker compose exec postgres pg_isready -U weekend -d weekend`).
3. Выполнить `npm run db:migrate` и `npm run db:seed`.
4. В отдельном терминале запустить `npm run storage:dev` (S3rver, loopback 9000, данные в `.storage/`).
5. Проверить `npm run storage:init`, затем запустить `npm run dev`.

`docker-compose.yml` содержит только PostgreSQL. S3rver — отдельный Node-процесс, не контейнер MinIO. Публичные демонстрационные значения в `.env.example` предназначены для локальной разработки. Настоящие credentials — только в окружении; не добавлять в Git и не выводить их значения.

Docker volume и `.storage/` на ПК будут новыми: облачная база и объекты не мигрировались. Seed идемпотентно записывает 24 демо-места. В облаке синтетические видео E2E были удалены, пользовательского production-хранилища не настраивали.

Браузерное сохранение на домене Vercel и на localhost — разные localStorage. Оно не переносится автоматически. В интерфейсе можно скачать JSON-план поездки; импорта такого JSON пока нет.

## Что реализовано

- Next.js App Router / TypeScript / React / Tailwind CSS; компоненты Button/Dialog в стиле shadcn/ui на Radix/CVA; иконки lucide; локальные шрифты Inter.
- Большая MapLibre-карта, вертикальные миниатюры точек, кластеры, зум, плавное перемещение, связанная визуальная лента.
- Поиск по названию, городу и региону, категории, закладки, коллекция сохранённого, пустые/загрузочные состояния.
- Карточка выбранного места, переключение между местами, горизонтальные свайпы на телефоне, добавление в поездку. На mobile — нижняя панель и закреплённые кнопки.
- Один активный HTML5-плеер MP4/WebM: autoplay muted, loop, play/pause, звук, poster, обработка ошибок. Не запускается множество видео на карте. Собственный загруженный файл получает thumbnail из декодированного кадра.
- Форма импорта с координатами или выбором на карте, названием, описанием, городом и категорией. Можно локально сохранить карточку внешней ссылки.
- YouTube — официальный privacy-enhanced embed после нажатия и ссылка на оригинал. TikTok/Instagram — переход к оригиналу; чужие видео не скачиваются.
- Серверная загрузка собственного видео в S3 до 50 МБ, ограниченное чтение потока, проверка MP4/WebM, случайный ключ объекта. `/api/media/` выдаёт приватный объект с HTTP Range.
- PostgreSQL/Prisma: Place, Video, Trip, TripStop. Клиентское состояние — Zustand + localStorage.
- Поездка до 20 точек: удаление, стрелки порядка, ближайшая следующая точка с сохранением первой остановки, авто/пешком, бюджет 1/2 дня, JSON-экспорт, серверное сохранение и ссылка на навигацию.
- OSRM-расчёт дорожной линии, расстояния и времени при доступности сервиса. При ошибках или слишком далёком snap к дороге — подписанный пунктир по прямой без выдуманного времени.

## Важные технические решения

Prisma и generator пакеты закреплены на **7.10.1**. `npm run db:generate` вызывает официальный in-process JS-generator с npm-distributed WASM, потому что облачная сеть блокировала сервер нативных Prisma engines. Проверки TLS/checksum не отключались. Не заменять этот путь на голый `prisma generate`, не проверив среду и совместимость.

`npm run db:migrate` — самостоятельный transactional SQL runner с advisory lock и SHA-256 проверкой применённой миграции. Журнал — `_weekend_migrations`, а не `_prisma_migrations`. Не смешивать с `prisma migrate deploy` без осмысленного перехода. Seed не удаляет импортированные места.

Порядок поездки — nearest-neighbour по географическому расстоянию, не глобальная оптимизация по дорогам. Первый пункт фиксирован. При изменении поездки старый расчёт сбрасывается; ответ от уже устаревшего запроса не применяется.

## Реальные ограничения текущего MVP

- 24 **реальные географические точки**, но нет готовой лицензированной подборки travel-видео. Не выдавать одноцветные тестовые MP4 или случайные ролики за съёмку мест.
- Для демо используется **одна повторяемая фотография региона**, не отдельная фотография каждой точки. Это прямо подписано. Учебный источник не даёт отдельной production-лицензии; перед публичной коммерческой дистрибуцией заменить на собственные/лицензированные фото конкретных мест. См. CREDITS.
- Первые 10 секунд UX — главное направление дальнейшего улучшения; настоящие медиа сильно улучшат нынешний демонстрационный экран.
- Фильтры кафе/отелей изначально пусты: вымышленных организаций, цен, часов работы и наличия мест нет.
- Локальные Natural Earth полигоны — обзорная карта, не дорожная навигация. При доступности онлайн автоматически подключается стиль OpenFreeMap.
- Полная карта использует `tiles.openfreemap.org`; дорожный routing — `router.project-osrm.org` (настраивается `ROUTING_URL`). Нужен отдельный OSRM-compatible `WALKING_ROUTING_URL` для настоящих пеших маршрутов.
- К островам нужен водный транспорт. Дорожный snap дальше 1,5 км отвергается; в fallback нет вымышленного времени.
- Фильтр времени из Сортавалы — грубый радиус по прямой / 55 км/ч, с подписью. Время посещения — плановая оценка.
- «Два дня» задаёт бюджет; автоматического ночлега/расписания по дням нет.
- Пользовательские аккаунты, оплата, бронирования и соцфункции по исходному scope не нужны. Пока нет разграничения владельцев/модерации. Перед публичным открытием серверных загрузок нужен контроль доступа/квот.
- На Vercel большой MP4 через текущий serverless handler ограничен лимитом тела платформы: для production-загрузок нужна прямая подписанная загрузка в S3. Для текущего онлайн-демо PostgreSQL/S3 не подключали.
- Сохранение Trip на сервере реализовано, но отдельного интерфейса библиотеки/загрузки ранее сохранённых серверных поездок нет. Текущая поездка восстанавливается из localStorage.

## Проверки и что известно достоверно

Команды:

```sh
npm run lint
npm run typecheck
npm test
npm run build
```

На облачной машине проходили lint, typecheck, production build и **8 тестов Vitest** (5 география/данные/валидация + 3 API routing). Успешный ответ OSRM покрыт fixture-ответом; это не проверка доступности публичного сервиса.

**6 E2E Playwright** проходили в Chromium desktop и mobile-эмуляции: карта, карточки, категории/пустые результаты, localStorage после reload, поездка, сохранение в PostgreSQL, synthetic own MP4 → S3 → место → HTML5 playback/pause → HTTP Range, ошибки API.

Для E2E нужны полный локальный стек, FFmpeg, Chromium. В локальной среде можно установить браузер `npx playwright install chromium`; при системном браузере настроить `CHROMIUM_PATH`. Конфигурация автоматически пробует `/usr/bin/chromium` на Linux, иначе bundled Playwright Chromium. Отдельные проверки на настоящих Safari/iOS/Android не проводились.

E2E пишут синтетические тестовые места/объекты. `npm run test:cleanup` удаляет только записи с точным тестовым префиксом и описанием и их MP4. Использовать отдельную тестовую БД при общей эксплуатации.

После E2E была исправлена CSS-иерархия слоёв: маркеры не перекрывают нижнюю карточку места. Это дополнительно проверено mobile screenshot и hit-test; финальный build прошёл.

Локальное демо без `.env.local` дополнительно проверено из распакованного архива: чистая установка, 24 точки, карта, выбор места и восстановление поездки. Сам ПК пользователя этой сессии не был доступен — локальные возможности заново проверить в новом чате.

## GitHub / Vercel и окружение

Vercel: Node.js 24.x, Next.js, root `./`, `npm ci`, `npm run build`, output default. Для демо не задавать `DATABASE_URL` и `S3_*`. Credentials не в репозитории. `.env.local`, `.vercel/`, `.storage/` и generated outputs исключены.

Облачная сессия могла работать с Git через платформенный HTTPS proxy и уже отправила реализацию в `main`. Это не означает, что на ПК автоматически есть GitHub CLI login, Vercel login или SSH keys. Сначала проверить реальные bindings/логин и Git remote, значения токенов не печатать.

GitHub API (`api.github.com`) и API/страницы Vercel из облака блокировались прокси 403; login flow Vercel не доходил до device-code. Это ограничение **той облачной среды**, не доказательство проблемы на ПК или с аккаунтом пользователя. Домены были добавлены в черновик настроек, но фактический доступ не подтверждался. Пользователь самостоятельно подключил GitHub/Vercel, ссылку нашли на странице репозитория, пользователь подтвердил, что приложение открывается. Прямого просмотра live-деплоя из облака не было.

Не выполнять повторный Vercel deploy/создание второго проекта без необходимости: уже существует `v0-travelmap-iota.vercel.app`. Сначала выяснить существующий проект, аккаунт/команду и Git integration. Авторизация — официальный browser/device flow, пользователь подтверждает сам. Не переносить облачные access tokens в локальный проект.

3. Если пользователь ещё не клонировал проект, помочь клонировать в выбранную папку. Если папка уже есть — использовать её и сохранить пользовательские изменения.
4. Запустить лёгкий browser-only demo (Node 24, `npm ci`, `db:generate`, `npm run dev`) и, если доступен browser tool, открыть его на **ПК пользователя**. Не требовать базу/S3 ради оценки интерфейса.
5. Показать/проверить desktop и mobile; согласовать следующий продуктовый шаг по новой обратной связи. Не выдумывать уже принятые изменения дизайна.
6. Дальше выполнять цикл изменений и релевантных проверок, push в существующий репозиторий согласно указаниям пользователя, проверять автодеплой по фактическим статусам. Не считать удачный push доказательством успешного production deployment.
