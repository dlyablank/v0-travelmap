# План: создание поездки и полный маршрут

## Исследованное поведение

- `components/explorer.tsx` открывает `TripPanel` как Radix Dialog из desktop/mobile-кнопок и `TripStopsStrip`; содержит удаляемый `.map-nudge`.
- `components/trip-panel.tsx` объединяет выбор локации, расписание, car/walk, рекомендации, перестановку, скачивание JSON и серверное сохранение. Сейчас длительность можно менять через select, внешняя навигация ведёт в Google.
- `lib/day-plan.ts` предпочитает ручное `settings.visits` значению `Place.visitMinutes`. Последнее есть в редакционных данных `lib/data.ts`, `lib/kolomna-data.ts`, пользовательских местах и БД; доказательств статистического происхождения нет.
- `lib/store.ts` хранит поездки и настройки по локациям в localStorage; hydration и объединение demo/server/custom сейчас выполняются в Explorer. Новая страница должна работать и при прямом открытии.
- `app/api/route/route.ts` вызывает OSRM с `steps=false`, отдаёт только геометрию/дистанции/время. Без walking URL или при ошибке возвращает straight-line без выдуманного времени. `lib/types.ts` не содержит инструкций.
- `app/api/trips/route.ts` сохраняет только базовую поездку и порядок точек; расписание уже сохраняется локально и в JSON, не заявлять обратного.
- Регламент в `HANDOFF.md`; действующего task tracker не обнаружено на момент плана.

## Пользовательский сценарий и UI

Обязательное уточнение: добавить общественный транспорт (`transit`). В этом режиме не вызывать driving/walking provider и не обещать локальных актуальных рейсов. Переход описывается «Общественным транспортом: [A] → [B]», с действием «Посмотреть транспорт и пересадки в Яндекс Картах» для пары точек. Также дать ссылку на всю поездку. Время/дальнейшее расписание неизвестны без транспортного источника; это явно объясняется. Этот переход к актуальному внешнему планировщику согласован координатором как сценарий текущей поставки; внутренний поиск рейсов не требуется.

Пользователь добавляет места в поездку из карты, карточек, видео или сохранённого, открывает «Моя поездка» и попадает на `/trip`. Также страница доступна напрямую. Видит локацию, время начала/окончания дня, режим движения, список остановок с автоматически выбранной длительностью; может добавить доступные места, удалить или переставить их. Сохранить переход к каталогу для выбора мест и возврат обратно без потери поездки. После построения видит отдельный, явно обозначенный итог: старт, все остановки по порядку, описания мест, время посещения, каждый переход с пунктами «откуда → куда», способом движения, доступными расстоянием/временем и инструкциями. Для авто — заметная ссылка «Маршрут в Яндекс Картах» со всеми точками в фактическом порядке.

Desktop: полноценная страница с читаемой шириной контента, блоками настройки и итога, навигацией назад к местам; допускается две колонки при достаточной ширине. Mobile: одна колонка, обычная прокрутка страницы, доступные действия и ссылки, без перекрытия таймлайна нижними кнопками. Сохранить текущую палитру, обложку и визуальную иерархию; убрать ограничения ширины бокового диалога. Контролы с понятными label, фокусом и размером действий около 44px. Итог не должен требовать чтения карты для понимания порядка поездки.

Уточнение всех упоминаний ссылки «на всю поездку» ниже: одна Яндекс-ссылка поддерживает не более 10 точек. При 11–20 точках вместо неподдерживаемой единой ссылки дать последовательные части с общей граничной остановкой и ссылки по переходам; все точки остаются доступны в порядке плана. Например, 20 остановок: части 1–10, 10–19, 19–20. Подписи сообщают номер части и диапазон остановок, а пояснение — ограничение Яндекса. Это относится ко всем трём режимам. Основание: [официальная справка](https://yandex.ru/support/maps/ru/concept/rout), [официальная документация URL](https://yandex.com/dev/yandex-apps-launch-maps/doc/en/concepts/yandexmaps-web).

## Мини-задачи и зависимости

1. **Основа страницы и навигация.** После установки прочитать локальные Next docs установленной версии, если доступны. Добавить `app/trip/page.tsx` и клиентский экран поездки; переиспользовать/выделить существующий `TripPanel`, убрав оболочку Dialog для этого сценария. Вынести общий bootstrap мест/hydration в небольшой hook либо иной общий модуль. Перевести все входы в поездку на `/trip`, обеспечить прямой URL, reload и возврат в каталог. Данные карты и видео не терять. Удалить `.map-nudge` с обеими надписями. Зависимостей нет.
2. **Автоматическая длительность.** В `dayPlan` использовать `place.visitMinutes` независимо от старых overrides. Убрать select, старые подсказки о редактировании и совет «сократите посещения». Показывать read-only длительность и честное пояснение происхождения оценки. Старый storage читать без поломки поездки; начало/конец дня сохранять. Зависит от 1 для UI, вычисления независимы.
3. **Данные переходов.** Расширить тип каждой leg необязательными нормализованными инструкциями. Запросить OSRM steps, преобразовать подтверждённые maneuver/name/distance в читаемые указания без выдуманных названий. Отсутствующие steps не ломают старые fixtures/маршруты. Неизвестный maneuver отображать нейтрально либо оставить исходное подтверждённое название дороги, не выдумывать поворот. Сохранить таймаут, отмену и straight fallback. Для walk использовать только walking-провайдер. Зависимостей от UI нет.

   В рамках этой же мини-задачи: расширить тип режима до `car | walk | transit` в store, RouteResult, API и потребителях. Для transit API возвращает явно предварительную схему переходов с неизвестным временем и сообщением об актуальных вариантах в Яндексе, без сетевого вызова OSRM; географическое расстояние обозначается только как «по прямой». Исключить рекомендации, рассчитанные на дорожные объезды, для transit. В API сохранения поездки принять transit, в Prisma проверить поле transportMode (если String, миграция не нужна; если enum — потребуется совместимая миграция).
4. **Итог и Яндекс.** Представить весь маршрут: список всех остановок с описаниями и каждого перехода с явными началом/концом, режимом, доступными метриками и инструкциями из 3. Добавить helper формирования Яндекс URL с координатами latitude,longitude в порядке таймлайна, `rtt=auto` для авто, `rtt=pd` для пешего fallback. Проверить формат по официальному источнику при реализации. Смена порядка/локации/режима инвалидирует старые данные; отменённый ответ не подменяет новый итог. При straight честно указать «по прямой», отсутствие реального пути/времени и возможность уточнить путь по внешней ссылке. Дополнить существующий JSON результатом с инструкциями и актуальными длительностями. Не менять серверную схему ради этой задачи. Зависит от 1–3.

   Для transit helper должен формировать транспортный режим Яндекса `rtt=mt`, подтверждённый официальной URL-документацией (для car — auto, walk — pd, rtext — latitude,longitude через ~). Нужны ссылки для каждой пары и всей поездки с учётом лимита: до 10 точек — одна общая ссылка, свыше 10 — последовательные части максимум по 10 точек с общей граничной остановкой. Для 20 точек это 1–10, 10–19, 19–20. Дать понятные подписи частей/диапазонов и пояснение ограничения; все точки и порядок должны сохраняться в совокупности ссылок, ссылки по переходам также доступны. Не отправлять 20 точек в одну ссылку и не обрезать их молча. Правило применяется к car/walk/transit. Сохраняются три режима в локальных данных и JSON; серверное сохранение принимает transit.
5. **Проверки и отчёт разработчика.** Адаптировать существующие E2E с dialog-селекторами к странице; добавить содержательные unit/API/E2E для новых требований. Выполнить доступные lint/typecheck/test/build, затем браузерные проверки на desktop/mobile. Сохранить implementation.md с фактическими результатами и ограничениями. Зависит от 4.
6. **Независимое QA отдельного тестировщика.** Координатор передаёт отдельному субагенту-тестировщику исходный сценарий и критерии ниже; тестировщик проверяет их самостоятельно и сохраняет результат в qa.md. При FAIL координатор передаёт исправления разработчику. Зависит от 5; разработчик не выставляет итоговый PASS.

## Затронутые модули

Основные: `components/explorer.tsx`, `components/trip-panel.tsx` (либо выделенный экран), новый `app/trip/page.tsx`, `app/globals.css`, `lib/day-plan.ts`, `lib/types.ts`, `lib/store.ts`, `app/api/route/route.ts`, `app/api/trips/route.ts`, небольшой общий модуль загрузки мест/hydration и helper Яндекс URL. Компоненты обложки/полоски/рекомендаций, `lib/recommendations.ts` и все сигнатуры `car | walk` привести к трём режимам без неверного отображения transit как walking. Данные посещения и Prisma не переписывать без причины. Тесты: `tests/day-planner.test.ts`, `tests/route-api.test.ts`, `tests/routing.test.ts`, `tests/e2e/day-planner.spec.ts`, связанные journey/explorer/regions сценарии с переходами в поездку.

## Критерии приёмки

1. На desktop и mobile обе заданные надписи и весь их пустой декоративный блок отсутствуют; выбор карточки/карта продолжают работать.
2. Каждый доступный вход «Моя поездка» открывает отдельную `/trip`, а не диалог. Прямой вход и reload работают; есть понятный возврат к местам. Выбранные точки и сохранённое не пропадают при переходах и возвращении.
3. В планировщике нет редактирования длительности посещения. Расписание, итог и JSON используют `Place.visitMinutes` для каждой точки; сохранённые ранее `visits` игнорируются. UI не заявляет измеренную статистику, честно называет величины ориентировочными.
4. Выбор локации сохраняет раздельные поездки и настройки начала/конца; порядок, удаление, добавление сохранённых и существующие рекомендации продолжают работать. Максимум 20 точек. На странице есть доступный способ найти/добавить места, включая возврат в каталог.
5. При 0 остановок есть понятное пустое состояние и действие выбора мест; при 1 остановке видна её длительность и пояснение о минимуме двух для построения. При конце дня раньше/равном началу показана ошибка, построение недоступно. При переполнении дня показано предупреждение с предложением убрать остановку/изменить границы дня, без предложения вручную сократить посещение.
6. При загрузке мест/hydration не показывается окончательное ложное пустое состояние и не теряются сохранённые id; есть индикация. Во время расчёта есть статус и предотвращение повторного запуска. Ошибка запроса видна, доступен повтор; отменённый/устаревший ответ не заменяет маршрут после изменения точек, режима или локации.
7. Успешный итог явно содержит старт, финиш, все остановки в текущем порядке, описание каждой и автоматическую длительность, расписание при известных временах, доступные суммарные расстояние/время и каждый из N−1 переходов с названиями обеих точек и способом движения.
8. Для корректного walking fixture с данными steps каждый переход содержит понятные инструкции из фактических манёвров/дорог. Для автомобильного маршрута итог содержит описание движения между точками и доступные указания. Нет выдуманных дорог, пешеходного времени из driving-профиля, рейсов или статистики.
9. При ненастроенном walking URL, недоступности сервиса или недоступных точках итог честно помечен предварительным: расстояние по прямой, время пути и дальнейшее расписание неизвестны, реальных инструкций нет. Есть пояснение и внешняя ссылка для уточнения пути. Реальная онлайн-доступность walking provider не обязательна для fixture/fallback QA; непроверенное онлайн-покрытие явно указано в отчёте.
10. Яндекс-ссылки открываются в новой вкладке безопасным внешним link; автомобильные используют auto, пешие — pd, транспортные — mt. При 2–10 точках общая ссылка содержит все точки в фактическом порядке. При 11–20 точках показаны последовательные части максимум по 10 точек с общей граничной остановкой, понятными номерами/диапазонами и пояснением лимита Яндекса; также доступны ссылки по переходам. Совокупность частей содержит все точки и все N−1 переходов в порядке плана без пропусков. Например, 20 точек дают 1–10, 10–19, 19–20. Перестановка/удаление/смена локации обновляют ссылки; нет ссылки на старый маршрут. Генерация координат, лимита, границ частей и полного порядка проверена автоматически; браузером проверены подписи, href и переход, если внешняя сеть доступна. Единая неподдерживаемая ссылка на 20 точек не требуется.
11. На desktop 1440×1000 и mobile iPhone 13 страница, итог, инструкции и действия доступны без горизонтального overflow, обрезания текста или перекрытия контента. Клавиатурная навигация и label основных полей работают. Работающий сайт осмотрен в браузере, получены desktop/mobile скриншоты.
12. Скачивание JSON содержит актуальный полный маршрут/длительности/переходы. Существующее серверное сохранение сохраняет порядок и режим; при недоступной БД даёт честное сообщение о локальной копии, не обещает сохранённого на сервере расписания.
13. Пользователь может выбрать общественный транспорт. Весь итог и каждый переход обозначены этим режимом; для всех N−1 переходов есть описание A → B и корректная ссылка на актуальный транспорт/пересадки в Яндексе, а также действие для всей поездки либо честно объяснённое ограничение внешнего сервиса. Время поездки не берётся из car/walk и не выдумывается, последующие arrival/finish неизвестны, первая остановка и длительности посещения остаются доступны. Переключение car → transit → walk инвалидирует старые данные, режим переживает reload и скачивание, принимается API сохранения. Рекомендации дорожных объездов для transit не показываются.

## Проверки и тестовые данные

- Unit: две точки по 60 мин и 10 мин пути дают 130 мин; legacy override не меняет 60 мин; неизвестная duration оставляет последующие времена null; границы дня и overflow; Яндекс URL для 2, 3, 10, 11 и 20 точек во всех трёх режимах. Проверить максимум 10 точек в каждой части, общую граничную остановку, покрытие всех N−1 переходов и восстановление исходного порядка после удаления повторной границы. Для 11 точек ожидаются диапазоны 1–10 и 10–11, для 20 — 1–10, 10–19, 19–20; проверить парные ссылки и обновление при перестановке.
- API: fixture OSRM с несколькими манёврами и без steps; malformed/error response, удалённое snap, отсутствие walking URL; отсутствие выдуманного времени у straight.
- E2E: Коломна (кремль, Лажечникова, третья близкая точка), смешанный legacy storage двух локаций с visits; прямой `/trip`, переходы/возврат/reload, добавление/перестановка/удаление, оба режима, mocked success и failure/fallback, загрузка и пустое состояние, скачивание.
- Запуск: npm run lint, npm run typecheck, npm test, npm run build; npm run test:e2e для planner и связанных изменённых навигационных сценариев. Никаких разрушительных операций на рабочей БД.
- Браузер: Playwright Chromium по существующему конфигу. Проверки маршрута детерминированы fixture-ответами; отдельно прогнать реальный fallback без walking URL. Недоступность браузера означает BLOCKED для обязательного визуального QA.

## Существенные вопросы и ограничения

- Пользователь подтвердил общественный транспорт. Обязателен критерий 13 и описанное расширение мини-задач 3–4. Встроенный поиск актуальных линий не имеет источника; согласован переход в Яндекс с каждой пары остановок. Без новых данных не обещать локальные рейсы и времена. Тесты дополнить transit API (без fetch OSRM), ссылками и browser-переключением/reload.
- Источник реальных средних посещений отсутствует; в этом объёме используются согласованные с координатором редакционные оценки.
- Полноценные реальные пешие инструкции доступны только при наличии провайдера. По согласованию текущая поставка поддерживает его данные и честный внешний fallback без обязательного развёртывания новой инфраструктуры.
