# Запрос: отдельная страница поездки

Дата: 21 октября 2026. Исходный запрос пользователя сохранён без изменения смысла:

1. Хочу убрать **Увидеть. Влюбиться. Отправиться.&#x20;**&#x41D;ажмите на карточку и начните свою историю - надпись
2. Хочу чтобы при составлении маршрута не было возможности указывать время на месте, а ставилось столько, сколько в среднем проводят люди
3. Нужно сделать план более удобным - отдельную страницу создания поездки. А итоговый план должен описывать весь маршрут, содержать описание того как добраться (если на транспорте, пешком) и ссылку на составление маршрута на Яндекс карты, если на авто.

## Подтверждённые требования

Последующее уточнение пользователя: **«Также общественный транспорт»**. Это обязательное требование. Координатор согласовал осуществимый сценарий: третий режим `transit`, описание каждого перехода и ссылка на общественный транспорт в Яндекс Картах; актуальные линии/пересадки доступны там, без источника время неизвестно. Не использовать автомобильный маршрутизатор для расчёта общественного транспорта.

- Удалить блок с обеими указанными надписями.
- Убрать выбор длительности посещения из планировщика; автоматически учитывать длительность каждой остановки.
- Перенести создание поездки на отдельную страницу.
- Итог описывает весь маршрут и перемещения между остановками; автомобильный маршрут открывается в Яндекс Картах.
- Сохранить архитектуру Next.js/React/Zustand, данные, существующие локации и стиль интерфейса. Публикация не поручена.

## Допущения и согласованные с координатором технические границы

- В проекте есть редакционное `Place.visitMinutes`, но нет статистики посещений. Координатор принял использование этих оценок с честной подписью «Ориентировочно на месте»; нельзя называть их измеренным средним посетителей. Реальный статистический источник потребовал бы отдельного поручения и данных.
- К существующим `car` и `walk` добавить `transit`. Автобусные номера, расписания, пересадки и тарифы не выдумывать; реальные актуальные варианты открываются в Яндексе для каждого перехода и всей поездки.
- Поездка остаётся однодневной, в пределах выбранной локации, 2–20 точек для построения; первая точка — старт, последняя — финиш. Обратная дорога домой и многодневность не запрошены.
- Уточнение технической границы Яндекса: одна ссылка содержит максимум 10 точек (старт, финиш и 8 промежуточных). Для 11–20 точек показывать рабочие ссылки на последовательные части с общей граничной остановкой и понятными номерами/диапазонами частей; также доступны ссылки по переходам. Все точки и их порядок сохраняются в совокупности ссылок, единая неподдерживаемая ссылка на 20 точек не требуется. Основание: [справка о построении маршрута](https://yandex.ru/support/maps/ru/concept/rout), [официальный формат URL](https://yandex.com/dev/yandex-apps-launch-maps/doc/en/concepts/yandexmaps-web). Подтверждено координатором после проверки разработчиком, повторно сверено планировщиком.
- Для пешего режима использовать реальные данные настроенного маршрутизатора; без него показывать честное ограничение и ссылку Яндекс для пешего маршрута. Координатор согласовал такой fallback и проверку нормализации fixture-данными без обязательной доступности внешнего провайдера.
- Отдельная страница `/trip` заменяет диалог, итог находится на этой же странице после построения. Отдельный публичный URL сохранённой поездки не требуется.
- Старые ручные `daySettings.visits` не должны влиять на новый расчёт; начало/окончание дня, выбранные точки, избранное и разделение по локациям сохраняются.
- Внешних визуальных референсов нет; использовать текущие цвета, шрифты, карточки и компоненты.

## Доступы и ограничения

- Локально отсутствуют `node_modules`, в том числе `node_modules/next/dist/docs/`. Перед реализацией после установки зависимостей прочитать доступные руководства установленной версии про страницы, Link и клиентские компоненты.
- PostgreSQL необязателен для локального сценария, API уже поддерживает локальные места и честное сообщение о недоступности серверного сохранения.
- `WALKING_ROUTING_URL` опционален; отсутствие не скрывать. Секреты и значения окружения не заносить в отчёты.
- Существующие изменения `.codex/` и локальные правки пользователя сохранять.
